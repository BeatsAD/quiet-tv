# 使用 Agent 排查 Quiet TV 问题

[首页](../README.md)  [桌面配置与恢复](SETUP.md)  [Agent 安装与恢复](AGENT_INSTALL.zh-CN.md)

开发源码支持从“应用管理 → 诊断日志”标签扫码下载 Quiet TV 自身的关键事件和错误，无需 ADB。另提供手动启动的设置页面采集，需要电视已开放并授权本机 TCP ADB。该日志不包含完整系统日志。涉及厂商主页、进程被杀或应用无法打开等问题时，使用下述电脑侧 Agent 进一步采集只读现场。已发布旧安装包不会随源码变化自动更新。

## 采集厂商网络设置页面

需要定位“设置 → 网络 → 无线网络”的实际入口时，在“诊断日志”选择“采集设置页面”。应用按现有应用管理保存的 TCP 端口连接并核对本机及 Android 用户；未配置时沿用应用管理的 5555 默认端口，连接失败明确记录，不扫描其他端口、不自动开启调试或授权。连接成功后打开系统设置，用户按原来的路径进入目标页面，停留数秒，再返回“诊断日志”，选择“停止采集并生成”，扫码下载新日志。

采集由应用进程持有，离开诊断标签不会停止；最多三分钟，每次快照结束后间隔两秒。主动停止、息屏、超时、断连或用户核对失败会结束采集，不自动重连。普通日志导出仍无需 ADB；“重新生成”只导出当时已取得的结果，正在采集时会标明状态。

导出增加“系统设置页面采集”摘要和 `settings.capture` 时间线，包含采集编号、采样次数、变化数、未知数和结束原因。通过只读 [dumpsys](https://developer.android.com/tools/dumpsys) 提取恢复中的 Activity、焦点窗口组件、匹配 Activity 的启动 action、Fragment 类名候选及系统暴露的状态/hidden/added/detached/userVisibleHint 字段，以及实际组件的启用、导出和权限状态；同一个 Activity 内的 Fragment 变化也会记录。单项查询失败保留其他可读信息，并标明来源受阻；原始输出限制为每条命令512 KiB，超限不当作完整快照。

不保存原始系统转储、窗口标题、页面文字、网络列表、Intent URI 或 extra 值，只记录是否存在 Intent 数据/extra。Fragment 是 active/added 候选，不保证当前可见；采用普通 View 的内部切换可能无法识别，不能将“没有变化”解释成“用户没有操作”。采样可能遗漏短暂页面；进程被系统终止后不会自行续录，历史中只有 begin 而无 result 时应标为未完整结束。缺少 Fragment 或专用 Activity 时，仍可能需要进一步检查设置 APK 的入口声明和参数；观察到组件不代表第三方可直达，也不代表真机功能验收通过。

## 开始排查

需要一台电脑、能执行终端命令的 Agent，以及电视实际允许的 ADB 连接。已安装 `quiet-tv-diagnose` skill 时，输入：

```text
请使用 $quiet-tv-diagnose 帮我排查 Quiet TV 问题。
问题现象：<描述你遇到的问题>
请每次只指导我完成当前必要的一步，等我反馈后继续，最后生成可发给开发者的问题报告和反馈包。
```

Skill 由独立本地技能包交付，不属于 APK，也不参与主应用构建。安装技能包时将其中的 `quiet-tv-diagnose` 目录放入 Agent 的 skills 目录。没有安装 skill 或 Agent 不支持 skill 时，可以使用下列独立提示词；没有执行工具时，AI应逐步指导用户手工操作，不能声称自己已操作。

## 无 skill 的复制提示词

```text
你是 Quiet TV 排查助手。请在我的电脑上进行只读排查，并逐步指导我操作电视。
问题现象：<描述你的问题>

先检查电脑工具和 ADB 设备列表，让我确认目标电视；即使只有一台在线，也不要自动选择。后续命令始终指定这个设备。根据电视实际提供的调试入口指导我连接及完成电视授权，不猜端口，不记录配对码。能通过只读查询取得的信息请自行收集，无法读取的项目标为未知。

采集实际电视型号、系统/API、固件、Quiet TV 包名和版本、当前用户与相关现场。使用电视自身的 logcat --help、pm help 等帮助确定可用命令，不假设用户0或新系统命令存在。

在电脑上先启动持续 Logcat 采集，再逐步指导我复现问题。不要只抓 Quiet TV 的 PID，否则退出或崩溃后可能丢失相关系统日志。不要清空系统日志。记录采集起止时间，并把我每一步操作和观察单独记入时间线，区分用户反馈与系统证据。一次录制默认三分钟，必要时最长十分钟；我完成复现后停止采集，不无限录制。电脑休眠、连接断开、固件限制和日志截断必须报告。

只读排查，不安装、卸载、清数据、改默认桌面、启停系统包、改权限或重启。实体HOME、重启及待机唤醒的结果分别记录；系统HOME查询和ADB注入按键不代替实体遥控器验收。没有ADB时继续整理现象与复现步骤，并明确缺少系统日志，不反复绕过固件限制。

按固定分类输出：QTV-CONN-001（ADB采集前置受阻）、QTV-CAP-001（采集不完整）、QTV-APP-001（明确指向Quiet TV的Java崩溃）、QTV-APP-002（明确指向Quiet TV的ANR）、QTV-HOME-001（用户实际按HOME后结果异常）、QTV-UNKNOWN-001（尚未定位）。这些是内部分类，不是Android原生错误码。不要另编故障码；保留原始系统错误。确认了崩溃也不等于确认根因。

最终生成本地报告：案例编号、分类编号、电视及应用版本、最短复现步骤、预期/实际结果、关键报错与证据行号、已确认事实、疑似原因、缺失证据和未验证项。不要把其他应用的错误归给Quiet TV，也不能因没找到错误就断言没有故障。

对常见凭据、网络标识、设备标识及个人信息尽力脱敏。让我检查报告和相关日志后私下发给开发者，不自动上传、发邮件或提交Issue。
```

## 海信开机与 HOME 异常

海信／VIDAA Android 电视出现开机先进入聚好看／原厂首页、实体 HOME 回原桌面或历史停用后黑屏时，读取[海信开机接管排查](AGENT_INSTALL.zh-CN.md#海信开机接管排查)，按其中证据项采集 HOME 候选及有效优先级、厂商启动路由、API24+ 用户解锁状态和实际 APK 的 Direct Boot 能力。Android 4.4／5／6 不套用 Android 7.0 的解锁机制；黑屏、一次设置失败或启动后单次快照都不足以确认根因。

只读诊断仅提出候选方案，不执行该安装规范中的设备修改或电源测试。轻量临时 HOME、停用原桌面及动画替换分别判断，不能把未取得 APK／源码的教程写成已经实现或真机通过；报告具体证据和缺失项，不提前结论为“无法改造”。

## 反馈与限制

开发中的新版诊断技能增加 `--home` 专项快照：按实际 Android 用户查询无障碍授权、系统服务绑定和 AppOps，补齐固件 fingerprint／incremental 等字段；命令不可用或采集截断时保留未知。支持核对 `home.quiet.tv`、`com.coocaa.quiettv` 与 `com.ts.launcher`，同名 HOME 代理通过组件区分，不能仅凭品牌选包。组件识别不代替签名核验。只有明确的 Build 字段保留四段数字版本，普通日志继续脱敏网络地址。

新版技能的本地案例登记工具按 SHA-256 保存附件副本、每次提交清单和追加索引；人工案例卡与反馈报告不会被重新采集覆盖。收到后续日志时，先核对设备、固件、实际安装包及触发场景，再明确关联已有案例；相同哈希不自动表示同一设备或根因。结论分为“已有方案可用／需要专项修复／证据不足／当前固件受限”，每案记录证据、下一步、源码与真机验证边界。技能需独立更新，现有 APK 或旧技能不会自动获得这些能力。

桌面问题还需区分以下证据：

- 系统默认 HOME、厂商私有 HOME 路由、实际前台组件和用户看到的首屏分别记录。新版 `--home` 在基础快照之后，只读查询 `HOME.JM`；确认 JmLauncher 包记录后才读取 `persist.sys.home.selectpkg`。属性为空或不可读均不自动修复，也不自动选择它作为守护目标。
- 应用导出的诊断补充自身开机接收组件状态、可见 TCL 管理组件版本，以及 Android 11+ 最近最多5条自身进程退出记录。自启动授权、组件启用和后台清理豁免分别判断；退出原因码、信号或空历史都不足以确认厂商清理。旧系统明确记录接口不可用。该历史接口见 [Android ActivityManager 文档](https://developer.android.com/reference/android/app/ActivityManager#getHistoricalProcessExitReasons(java.lang.String,int,int))。
- 后续每个场景单独记录默认 HOME 是否保持、首次可见页面、最终页面、原桌面闪回、切换耗时和待机时长；恢复原桌面单独验收。新版技能提供结构化场景模板，随每次证据提交追加保存。上游报告、自动化测试、设备日志与用户观察保留各自来源，不自动生成固件执行规则或“已解决”状态。

应用开发源码已补充可恢复的 Google HOME 顺序处理、JM/VIDAA 私有路由、TCL 自身后台策略和 Fire OS 6 替代观察入口，适用条件和用户操作见[直接接管与固件专项](AGENT_ADAPT.zh-CN.md#原桌面与-home-代理恢复)。新日志中的 `takeover` 是操作及读回记录，`usageObserverBound` 是替代观察服务状态，`tclPolicyStatus` 是策略读取/写回结果；三者都不能替代实体场景验收。`incomplete` 表示需核对恢复，`rolled-back` 表示本次失败后恢复了操作前状态，`restored` 表示明确恢复原桌面。

电脑诊断与案例登记仍然只读，不会因为识别到适用方案而自动执行。固件全局调度参数、透明覆盖窗口、root 修改系统启动文件不作为通用修复。上游实测、源码已实现、自动化通过、系统读回与 Quiet TV 对应固件实测分别注明；不能将“上游已解决”误写为“未知方案”，也不能直接扩展为所有机型支持。

用户检查后私下发送报告和相关证据。没有复现成功、缺少连接或没有明显报错，也要记录缺失项并交付现象报告。AI输出是排查结论，不代表已修复。

电脑采集不依赖诊断页面保持打开；只要电脑和 ADB 连接仍正常，Quiet TV 退出后仍可继续采集系统日志。Logcat不等于每次遥控器按键记录，不能读取其他应用的私有日志；固件权限和日志缓冲区会影响完整性。收集方式应依据设备帮助以及 Android 官方 [ADB](https://developer.android.com/tools/adb) 和 [Logcat](https://developer.android.com/tools/logcat) 文档。

MiBOX3直接HOME补偿开发日志增加 `home_guard.key_observed`，记录实际投递到无障碍的标准HOME按下/松开、keyCode/scanCode、单调时间、过滤请求与拒绝原因；`home_guard.home_trigger` 通过 observation 关联后续启动 attempt。广播、启动请求和首页生命周期回报均不等于实体键上屏成功。服务未连接或系统未投递时可能没有该事件，不能据此认定用户没按键；不记录任意文本输入。具体配置见[配置说明](SETUP.md#桌面守护实验)。

需要统一只读快照时使用[适配指南](AGENT_ADAPT.zh-CN.md)中的 `device_selftest.py` 默认模式；不要为排查自动开启主动场景。用户明确要求修复后沿用该指南的预览、执行和复测流程。
