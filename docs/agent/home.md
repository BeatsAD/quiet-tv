# HOME、守护与 ADB 配置

[统一入口](../AGENT.md)。只在任务进入本阶段时读取；先完成[连接与任务记录](connect.md)，执行前后遵守[验收要求](acceptance.md)。下方是底层工具示例；Agent 应按[任务记录说明](session.md)通过 `agent_session.py run` 调用，由任务分配新记录路径。

## 海信开机接管排查

识别到海信／VIDAA Android 电视，且出现“开机先进入聚好看或原厂首页”“实体 HOME 返回原桌面”“停用原桌面后黑屏”时，Agent 必须进入本分支，再决定接管路线。用户继续使用原安装请求，无需另外指定“优先级”或“开机解锁”。非 Android 电视不适用。先完成已授权的只读检查，不因一次 HOME 设置失败、黑屏或 ADB 身份特殊，就直接结论为“权限不足、系统必须依赖原桌面、无法改造”。有明确权限拒绝时保留原始错误，但只据此说明该操作受限。

### AI 实际调用的开机桌面脚本

可执行入口为 [configure_boot_home.py](../../scripts/configure_boot_home.py)。它已接入 `install_quiet_tv.py --goal takeover`：首次安装先trial并登记基础试用通过，任务工具再沿用该APK进入配置；无标准 HOME 路线时继续现有兼容守护。若仅尝试标准 HOME、读回确认仍为原桌面且设备身份不变，也继续评估兼容守护；读回未知、出现其他 HOME 或涉及厂商属性的部分修改时停止，按记录核对恢复。`trial`、`update` 和只读验收不会调用写入路径。独立 Agent 必须从同一次 `latest.json.tools` 下载并校验索引列出的全部工具与规则，不能只复制本文或只下载一个脚本。

已有 Quiet TV、只需配置开机桌面时，AI 先执行预览，再在已有开机接管授权内以新记录目录加 `--apply` 执行，不要求用户另写命令：

```sh
python3 scripts/configure_boot_home.py --serial "$TV_SERIAL" --user "$TV_USER" \
  --record "$NEW_PREVIEW_DIR"
python3 scripts/configure_boot_home.py --serial "$TV_SERIAL" --user "$TV_USER" \
  --record "$NEW_APPLY_DIR" --apply
```

脚本拉取实际已安装 APK 并检查签名、包名、系统档位和 HOME 声明；API24+ 另核对主 HOME 或轻量 `BootHomeActivity` 是否提供 Direct Boot 入口，均缺失时停止配置，不凭最新源码假定旧 APK 支持。轻量入口默认关闭，仅在本应用已是默认 HOME 且没有其他正常 HOME 可用时，由首页自动启用；升级或停用原 HOME 后须先进入一次 Quiet TV，让首页完成核对。它只绘制启动背景，用户存储解锁后交回系统当前选定的 HOME。主首页继续在解锁后初始化，保留原桌面及代理路线的默认 HOME 行为。声明存在不证明入口已启用或冷启动成功，须核对实际组件状态并实测。单独配置不下载安装包，不重复更新主程序，也不新建常驻电脑进程。

脚本实际执行并读回系统默认 HOME；当设备品牌为海信／VIDAA、目标为用户0、本机存在启用的系统包 `com.jamdeo.tv.vod` 且它是 HOME 候选、`persist.vt.use_home_pkg` 当前值确为该包或 Quiet TV 时，复用项目现有海信路由，将该属性指向 Quiet TV。属性缺失、值不明、非系统包或非主用户时不试写，仅报告标准 HOME 的配置范围；不能把标准 HOME 成功说成厂商开机路由已修复。属性已匹配目标时不重复写。保留原桌面、应用数据、其他系统包及开机动画，不提升 HOME 优先级或冒用原厂包名。

API24+ 的轻量启动入口不必在选择 Quiet TV 前已经启用。新 APK 在进程启动、应用替换及开机时，按系统 HOME 和候选准备入口，全程不读取未解锁的用户偏好；仅 Quiet TV 是唯一普通 HOME 时启用，显式停用的组件保持停用。工具通过 `boot-home-v1` 和 `bootHome` 读回是否就绪，启用入口后再次核对 HOME。旧 APK 缺少接口时保留“启动入口未核对”的边界，不能用于新增停用原桌面的操作。

每次使用全新电脑私有记录目录，写入前保存设备／固件／用户、实际 APK 校验值、原 HOME、包状态及属性原值；逐步记录待执行、命令结果及读回值。执行中断、权限拒绝或读回不符时停止后续修改，显示实际错误，不自动重试、重启或扩大到禁用原桌面。仅 HOME 查询／设置能力缺失或目标不在候选中的已知无写入结果，才允许安装入口继续独立守护方案；已经尝试写入后失败，先处理记录中的未完成变更。

撤销本脚本实际尝试过的变更时，AI 使用该次 `record.jsonl`，先预览，再按已有恢复授权加 `--apply`：

```sh
python3 scripts/configure_boot_home.py --serial "$TV_SERIAL" --user "$TV_USER" \
  --restore-record "$OLD_RECORD_DIR/record.jsonl" --record "$NEW_RESTORE_PREVIEW_DIR"
python3 scripts/configure_boot_home.py --serial "$TV_SERIAL" --user "$TV_USER" \
  --restore-record "$OLD_RECORD_DIR/record.jsonl" --record "$NEW_RESTORE_APPLY_DIR" --apply
```

恢复重新核对目标、用户和固件，拒绝覆盖其他操作已经改变的现场；只恢复本次 HOME／海信属性原值，不执行记录中的任意 shell，不撤销安装或其他守护权限。原 HOME 已经是 Quiet TV 时，撤销仍恢复到该次操作前的状态，不冒称恢复原厂。需要恢复整个安装流程时，仍结合原安装与守护记录按下方“请求恢复原桌面”处理。

脚本返回成功只表示配置已写入并读回。AI 必须继续按本页授权要求让用户核验实体 HOME、普通重启、断电开机及待机唤醒，记录首屏和最终页面；不把守护延迟跳转描述为“开机立即进入新桌面”。站点工具更新后即可配置已具备能力的主程序，但不能让旧 APK 自动获得缺少的 Direct Boot 或厂商能力。

### 线索来源与适用边界

用户提供的视频文字版描述了“原桌面优先级 50、新桌面 0，使用约 12KB 程序在开机解锁前承接 HOME，停用原厂首页并更换聚好看开机动画”的成功案例。目前未取得原视频链接、型号／固件、完整命令或助手 APK／源码；这是一条待核实的候选路线，不是 Quiet TV 的真机验收或可直接执行的禁用规则。数字 50／0、包名 `com.jamdeo.tv.vod`、助手大小和无广告效果均不能复制为本机事实。

Android 的 [Direct Boot](https://developer.android.com/privacy-and-security/direct-boot) 从 Android 7.0／API24 引入；解锁前可运行组件须声明 `directBootAware`，需要持久数据时使用设备保护存储。Android 4.4／5／6 不套用该机制，继续查厂商启动、按键路由及组件依赖。用户存储未解锁与锁屏界面不是同一个状态，不能仅凭黑屏或 `Keyguard` 锁定推断 Direct Boot。

### 按现场证据分流

先补齐型号、完整固件指纹、API、目标用户、实际安装包及 HOME 形态、原桌面组件和包／组件状态。沿用上方已保存的恢复基线；不要求用户猜系统字段。结合固件支持的 HOME 查询、`dumpsys package`、`dumpsys user`、前台组件和相关启动日志读取下列证据；命令不支持或字段缺失标为未知，不以默认值补齐。

| 检查项 | 判断与下一步 |
| --- | --- |
| HOME 候选、有效优先级、默认 HOME 与实体按键后的前台组件 | 记录同一用户的实际候选与解析结果。若高优先级原 HOME 被选中，继续核对默认选择及厂商路由；不能只凭清单中的 priority 判定根因。普通应用请求正优先级可能被系统限制为 0，不把“改成 51／100”当成通用修复。规则见 [Android intent-filter](https://developer.android.com/guide/topics/manifest/intent-filter-element)。 |
| API24+ 开机时的用户存储状态及实际 APK 组件 | 核对启动当时是否未解锁、HOME 是否能在 Direct Boot 运行，以及是否出现访问凭据保护存储的异常。读取安装在电视上的 APK 清单，不能用最新源码替代。开机结束后已解锁的快照不能证明启动阶段没有问题。 |
| 默认 HOME 已指向 Quiet TV，但原桌面仍被拉起 | 按用户动作时间线核对实际启动组件及发起方，区分厂商显式启动、实体 HOME 私有路由、守护未绑定／配置丢失与系统重新解析 HOME，不只反复设置默认值。 |
| 停用后黑屏、启动卡住或 ADB 断连 | 先核对已有修改及恢复通道，按授权恢复有记录的原状态。不能据此证明永久系统依赖，也不能继续停用其他系统包试错；连接恢复后先读状态，不重放修改。 |
| LOGO、启动动画、视频广告和原厂首页 | 分别记录出现顺序、可识别组件及用户画面。HOME 接管和广告／动画处理独立判断，桌面直达不等于所有启动广告已消失。 |

需要重启、断电或待机复现时，沿用本页电源测试授权要求；没有授权或恢复通道时先报告缺失的启动阶段证据，继续其他只读检查。

### 轻量启动中转候选路线

只有证据指向解锁前 HOME 缺失或存储访问不兼容时，才进一步评估“Direct Boot 临时 HOME → 用户存储解锁 → Quiet TV”路线。先检查实际发布包是否已经具备该能力；现有包可以处理时优先复用，不重复安装助手。

候选助手应有可被系统选中的、`directBootAware` 的 HOME Activity，在解锁前显示最小页面且不读取凭据保护的偏好、数据库或媒体；解锁后再显式启动已核验的 Quiet TV 组件。应同时检查当前用户是否已解锁并监听 `ACTION_USER_UNLOCKED`，避免错过广播；不能把后台接收器收到开机广播当作桌面已显示。目标未安装、被禁用、启动失败或配置暂停时，应有可用的恢复入口，避免递归发送 HOME。无需冒用原厂包名或声称取得系统权限。

这描述的是实现与核验条件，不代表已经提供海信专用助手。普通安装流程只使用已发布、已核验且适配的包；缺少匹配助手时明确报告，不临时编译、改签或从不明来源下载安装。用户另行选择源码实验后，才准备针对该固件的实现、签名／包名／目标组件／哈希与恢复方案；构建成功仍不代表冷启动成功。已知权限拒绝和厂商强制路由也不会仅因加入 `directBootAware` 自动消失。

### 原桌面、动画与恢复

默认保留原桌面。本分支不授予禁用资格，不改写[固件规则](../../app/src/main/assets/setup-presets.json)；只有满足[可选禁用原桌面](install.md#首次安装试用默认桌面与可选管理)的本机条件且用户明确选择，才按实际组件操作。教程中的批量删除预装应用不是接管前置条件，不予复刻。现有保留原桌面的代理／守护与停用原桌面的路线不能混用，先核对各自依赖。

动画替换作为独立候选：先确定是应用广告、厂商设置还是系统动画文件，并核对可写权限、原文件／配置及恢复办法。未取得原方法时标为未确认，不把停用聚好看等同于替换系统动画，不提供通用系统文件覆盖命令；普通安装／接管授权不包含动画修改。

`pm enable com.jamdeo.tv.vod` 只可能恢复已安装且被停用的该包，不能恢复删除的其他应用、修改的动画、隐藏状态或原默认 HOME。仅在本机确认包身份、用户及原状态后生成对应恢复命令：原 `enabled=0` 与显式启用 `enabled=1` 分别按固件支持的 `default-state`／`enable` 处理；隐藏、卸载或组件单独禁用另按本机记录恢复，不统一替换成 `enable`。恢复后读回状态并验证原桌面，不能承诺“一条命令恢复原厂状态”。

交付分别列出候选路线、已确认原因、缺失证据、实际采用方案，以及实体 HOME、普通重启、断电冷启动、待机唤醒、广告／动画和恢复结果。未做的项目标为未验证；不将教程作者的成功、助手体积或源码能力写成当前电视已完成改造。


## 原厂同包名空壳中转候选路线

用户提出的方案是：定位原厂桌面实际文件和启动入口，准备同名空壳，在壳内承接开机／HOME 并显式拉起 Quiet TV，最后移除原厂桌面文件。将它记录为待核验的机型专项，不是已经实现或验收的通用方法。当前没有对应脚本、原厂同包名壳 APK 或可执行规则；不要将本节转成普通安装器命令，也不要把现有独立 HOME 代理、酷开中转或改包名主程序当作原厂应用替换。

### 只读调查示例

明确提出“原厂同包名空壳接管”或“同名壳接开机、拉起新桌面”时，从统一入口直接进入本节。先区分下文的名称含义并调查可行性；不因未安装 Quiet TV 转去首装，不用普通 `repair`／`takeover` 代替空壳调查，也不虚构新的空壳执行路线。

目标电视、当前用户及只读 ADB 检查已经确认时，按[任务记录](session.md)填写变量，使用同批工具和全新私有目录：

```sh
python3 agent_session.py start --serial "$TV_SERIAL" --user "$TV_USER" --intent inspect --session "$NEW_SESSION_DIR" --bundle "$BUNDLE_DIR/latest.json"
python3 agent_session.py plan --session "$NEW_SESSION_DIR" --route inspect --note "原厂同包名空壳候选调查；只读核对原厂路径、组件、签名、启动依赖和离线恢复条件"
```

`start` 会只读查询目标电视，`plan` 保存调查范围；二者不会自动完成下文的原厂文件取证。继续按实际支持的只读命令核对，将设备／固件／用户、原厂路径与组件、签名、分区和依赖、恢复证据、未知项及下一步保存到电脑私有调查材料。证据不足时，将真实结论与缺项填入 `INVESTIGATION_FINDINGS`，按受限结果记录：

```sh
python3 agent_session.py accept --session "$NEW_SESSION_DIR" --check inspection --status LIMITED --source agent --note "$INVESTIGATION_FINDINGS"
python3 agent_session.py finish --session "$NEW_SESSION_DIR"
```

此时应报告调查受限，不能报告已经完成替换或接管。用户要求先不连接、不操作电视，或尚无目标时，不执行上述建档及任何设备命令；先在电脑保存候选说明和待补证据，不能填造路径、签名或验收结果。广告与空壳目标同时提出时，分别建立广告任务和只读调查任务，沿用各自记录；纯分析阶段同样不为建档连接电视。

### 同名的含义与技术条件

- 应用显示名、APK 文件名、安装路径、包名和组件名分别核对。文件改名不改变包名；厂商若显式启动完整组件，仅同包名而没有原 Activity／别名也不能承接入口。
- Android 同一设备不能同时安装两个相同 application ID 的应用。覆盖更新要求包名相同、签名证书兼容或具有有效签名轮换证明，并满足版本要求；自行签名的同包名壳不能直接覆盖原厂包。不能把“先安装同包名壳，再删除原件”当成绕过签名的顺序。[Android 更新规则](https://developer.android.com/google/play/app-updates)
- 删除原厂文件后再安装也不会自动继承原厂签名、共享 UID、签名权限或厂商服务协议。系统特权还受镜像分区和权限清单约束；复制到相同路径不能证明兼容。[特权权限规则](https://source.android.com/docs/core/permissions/perms-allowlist)
- 原件位于只读系统分区时，先确认实际写入能力、SELinux 和启动完整性校验。Root 权限不等于原厂签名；分区可写也不代表修改后可启动。AVB／dm-verity 可能拒绝使用修改后的数据；普通 AI 安装流程不自动解锁、Root、改校验或刷机。[Verified Boot](https://source.android.com/docs/security/features/verifiedboot/verified-boot)

### AI 调查与实施材料

1. **只读定位**：从实际 HOME 候选、默认解析和厂商启动日志确认原包与完整组件，不能凭显示名猜包名。按本机支持的 `pm path` 和 `dumpsys package` 查询生效 APK、全部 split、版本、签名、当前用户状态及系统／更新系统应用身份。已更新的系统应用可能同时有系统原件和 `/data/app` 中的更新包，分别核对；无法取得原厂副本路径就保持未知，不能把其中一个当作全部。
2. **保存恢复材料**：保存原 APK／split、校验值、签名、清单、文件属主／权限／安全上下文、原 HOME 与本次设备／固件／用户记录，核对原包是否提供设置、输入源、遥控器、开机握手、共享进程或其他应用依赖。单纯“打开新桌面”不能替代这些能力。恢复材料须留在电脑私有目录，原系统分区完整性被改变时，仅有 APK 备份可能不足；还须核实本机离线恢复途径。
3. **准备本机空壳**：只有签名及部署机制已经核实，且用户选择该机型专项开发时，才准备壳源码、实际包名／组件、签名、APK 哈希和部署方案。壳负责接收实际厂商入口，检查目标已安装、可启动且未暂停，再用显式组件启动 Quiet TV；不向自己的包递归发 HOME。需要解锁前运行的 API24+ 设备按上文 Direct Boot 条件实现；Android 4／5／6 不照搬。开机广播、前台 HOME 和厂商显式启动是不同入口，收到 BOOT_COMPLETED 不证明能从后台拉起界面。[后台启动限制](https://developer.android.com/guide/components/activities/secure-bal)
4. **先验证中转与退路**：在已授权、可恢复的实验设备／固件环境中，核对系统实际加载的是壳及其预期签名／组件，分别验证实体 HOME、完整重启、断电冷启动、待机唤醒和实际相关的设置／HDMI 影音／遥控器／ADB。只测试独立包名的原型只能证明跳转代码，不能证明同包名替换成立。原厂组件将被移除时，壳的失败退路必须独立且可用，不能将已被替换的原组件写成恢复入口。
5. **原厂文件移除单独列项**：只有具体机型／固件的替换与离线恢复已经核实，且当前授权明确包含该台电视的原厂文件移除时，才准备独立的实施清单，逐项列出真实完整路径、原哈希、分区、依赖、影响和恢复步骤；普通 HOME 接管或禁用授权不包含此动作。重新核对哪个文件是原厂原件、哪个是当前壳；替换后 `pm path` 可能指向壳，不能直接将其结果作为删除目标。不得根据目录名推断应删除的文件。
6. **删除限制与完成条件**：移除文件不同于 `pm disable-user`，也不同于 `pm uninstall --user`；后者不能作为“系统原件已彻底删除”的证据。涉及目录、批量或递归删除时，按工作区规则只停止删除及其依赖步骤，列明实际路径和影响，由用户手动处理，不拆成脚本或多次单文件操作绕过。单个明确文件也须满足本机授权和恢复条件，不把删除原件作为默认收尾或安装完成条件。实施后再检查原件、壳和系统登记状态及真实启动效果，不能仅凭文件不存在就报告接管成功。

任一条件缺失、签名冲突、受保护分区不可写、启动依赖无法由壳满足或离线恢复未经核实时，停留在候选调查，不先删除原件来尝试安装。继续现有可恢复的默认 HOME、厂商路由或兼容守护。缺少的机型、完整固件、原始文件清单、签名与恢复证据逐项报告；不把其他电视的路径、原厂密钥或成功案例当作本机事实。

本节只补充候选方案与证据要求，不改变现有工具和普通安装请求的保留原桌面行为，不增加执行资格。系统原件已被删除或替换的恢复须使用该次专项的实际材料；`pm enable`、现有 HOME 恢复脚本或恢复出厂均不能被承诺为还原原始系统文件的方法。

## 兼容守护的权限与范围

仅当用户明确请求自动接管桌面或另行授权兼容守护，且实际安装包包含相应组件时，才配置兼容守护的无障碍、通知访问及写安全设置能力；使用实际包名和已核对用户。首次权限配置不等于开机验收。新开发版进入配置后默认为自动，后续重启无需重复确认；系统 HOME 仍属原桌面时不得报告默认 HOME 已修改，不因守护可运行而禁用原桌面。用户明确暂停后不得重启、重绑或更新替其打开。历史安装包不因本文更新而获得该能力。

本修复提供[电脑配置脚本及步骤](../SETUP.md#桌面守护实验)：电脑 ADB 已授权即可完成首次配置，无需等待 Quiet TV 内置 ADB 认证成功。预览后，在已有守护配置授权范围内使用 `--apply`；主动暂停的配置还须明确 `--resume`，不在只读诊断、首装基础检查或仅更新时执行。先核对指定电视、前台用户、原主页及实际 APK 的 `HomeGuardSetupReceiver`；旧包缺少所需能力时先说明版本差异，未获更新授权不自行安装。脚本保留原桌面与其他服务，权限写入、服务绑定、事件可用及实体接管分别确认。Android 5／6补偿需用量统计授权；Android 4.4不开放。端口连通、ADB 开关开启、内置握手超时均不能单独证明电脑 ADB 授权状态或固件封锁。

系统默认 HOME 已指向 Quiet TV，但实际按键、开机或唤醒仍进入原桌面时，可在 `device_maintenance.py repair` 或标准 `install_quiet_tv.py --goal takeover` 使用 `--native-observer`。底层 `configure_home_guard.py` 同样支持此选项，并可用 `--home` 指定实际原桌面候选。该模式保留系统 HOME，只观察原桌面窗口，不启用 MiBOX3 专用按键补偿；与代理、`--direct-home`、`--adb-only` 不混用。维护会沿用已配置的此模式，也会依据当前路线中有用户证据的场景失败补充观察；默认 HOME 解析成功或服务绑定成功不会触发此分流。仅更新、试用和只读检查不增加守护，正常原生 HOME 保持原路线。

守护恢复只依赖写安全设置权限，不要求亮度等功能使用的 `WRITE_SETTINGS`；前台检测、后台启动、通知或同步恢复分别检查。Android 13 及以上在明确配置守护时探测 `ACCESS_RESTRICTED_SETTINGS`；TCL 系列按名字探测 `APP_AUTO_START`、`AUTO_START`、`APP_ASSOC_START`、`ASSOC_START`。不支持与拒绝授权分别记录，不猜数字编号，原本已允许的可选权限不重复写入。

新实现把服务恢复和回桌面分开：进程、通知及同步入口共享有限恢复任务，已连接时不因恢复请求重新探测桌面。切源、息屏和屏保仅取消前台接管，不中断服务重绑；暂停或更换路线才结束两类任务。首页启动确认及一次补偿归同一启动尝试，明确 HOME 可补充该尝试，窗口和用量统计不另排平行重试。开机广播兜底在守护连接后结束，重复亮屏不延长本次唤醒检查。无障碍设置变化显示“守护恢复待核对”，AUTO／OFF、原路线和 ADB 独立选择均保留；历史 APK 仍按其实际能力处理。

撤回这次新增的可选权限时，先在明确恢复意图下暂停守护，再预览 `configure_home_guard.py --serial "$TV_SERIAL" --user "$TV_USER" --package "$QUIET_PACKAGE" --restore-record "$GUARD_BEFORE_JSON"`，执行时加 `--apply --record "$NEW_PRIVATE_RECORD"`。工具核对设备、固件、用户、包名、原值和执行读回，只恢复该记录确认从非 allow 改为 allow、当前仍为 allow 的命名权限；当前模式不同则保留并记录。系统不提供同模式重复授权的来源历史，若之后有人重新授予相同的 allow，需先核对该授权是否仍要保留。此操作不撤销原有授权、不恢复整份无障碍／通知服务列表，也不恢复系统 HOME；后者使用原桌面恢复分支。记录不完整或写入后读回失败时，不自动推断成功或自动回滚。

共享恢复任务首次检查后，在 5、10、20、35、65、125 秒有限复查；重复进程、通知和同步回调加入同一任务，不延长窗口，已有重绑不会并行启动。锁定时只等待解锁；暂停、目标失效、权限缺失或守护连接会停止相应恢复。通知监听销毁不再取消共享重绑。超过窗口不常驻轮询，新的外部信号可补一次检查，原截止时间不变；真实断连或进程重建可开始新窗口。维护快照继续使用 `listenerRecovery` 和 `listenerRecoveryAttempt` 记录停止原因与请求次数，保留字段兼容；`bindingRecoveryPending` 与 `homeRequestPending` 分别表示服务恢复和桌面启动待完成，均不代表实体场景验收通过。



## ADB 常开与重启验收

### 安卓 4.x 的调试开关恢复

兼容档支持独立的 ADB 调试开关恢复，默认关闭；仅在应用实际拥有 `WRITE_SECURE_SETTINGS` 权限且用户明确开启后写入，并读回核对。API17 起使用 Global，较早系统使用 Secure；不授予权限、不提权，不把电脑或本机 ADB 已连接当作应用拥有写权限。旧版不恢复 TCP 端口、不创建同步恢复账号，不启用标准桌面守护。关闭保持选项后停止后续恢复，不关闭当前调试开关。

下方独立配置命令现支持 API17～20；旧版仅接受 `--adb-only`，先检查实际 APK 的 `adbOnlySupported`、`adb.permissionGranted`，缺少权限时停止启用。允许关闭已保存的选项；不尝试 `pm grant` 或写厂商属性。API14～16 的设置适配保留在应用内，本电脑工具未扩展到这些版本。旧 APK 没有能力回执时不继续。

兼容档保留开机广播权限；开机和应用升级仅恢复之前启用的调试保持或 API19 本机守护。两者独立：暂停桌面守护不关闭独立 ADB 保持，关闭 ADB 保持也不停止已配置的桌面守护。调试开关恢复仍不证明网络端口重开、授权保留或重启后能重新连接，须逐固件验收。

### API18 窗口桌面守护

Android 4.3 的兼容包提供 `window-home-guard-v1`。标准 HOME 选择无法完成、用户明确选择兼容守护时，先检查实际安装包的能力及 `windowHomeGuard.candidates`，指定本机已启用的系统 HOME 完整组件。电脑 AI 沿用原任务记录执行预览，再在已有接管授权内加 `--apply`：

```sh
python3 device_maintenance.py repair --serial "$TV_SERIAL" --user "$TV_USER" \
  --package "$QUIET_PACKAGE" --window-guard --home "$ORIGINAL_HOME" --record "$NEW_PRIVATE_RECORD"
```

工具只合并登记自己的 API18 无障碍服务并读回，保留其他服务、系统 HOME、原桌面及应用数据，不授予应用写安全设置权限，不依赖本机 ADB、使用统计或通知访问。已有暂停选择须用户明确恢复后加 `--resume`；仅检查、更新和试用不启用。后续 `repair` 沿用已保存的窗口路线，`pause`／`restore` 暂停该守护，不需要固件提供 `set-home-activity`。

守护仅接受新鲜的精确原主页／Activity alias 目标事件，保留用户打开原桌面与切源的放行，不根据包名抢回设置或播放页面。它显式拉起 Quiet TV，不修改默认 HOME；Android 4.3 的 HOME 后应用切换时序仍须实测。配置限定当前固件与原桌面版本，变化后须重新核对。系统负责绑定并在开机后恢复已登记服务，暂停状态跨进程保留；没有新鲜页面事件时不猜测前台，也不承诺厂商固件永久常驻。

配置读回不代表服务已绑定、实际事件已收到或实体 HOME 已通过。逐项记录绑定、真实页面事件、实体 HOME、退出应用、重启／冷启动、待机唤醒、设置／HDMI及恢复结果；乐视 S50 Air 的报告只提供故障线索，本路线尚无该固件验收。旧包没有此能力时停止依赖步骤，不把后续源码当作已安装能力。

### 乐视 Android 4.3：先分清原厂入口与实际窗口

开发源码补充了 `com.stv.deskplatform.ui.activity.ExternalJumpActivity` 后面的真实主页 `com.stv.deskplatform.ui.activity.Launcher`。只有前者是已选的可用系统 HOME、后者在同一包中存在且启用时，API18 窗口守护才把后者也作为观察目标；不按整个包抢回设置、播放或其他页面。依据是 [Aerial 的乐视入口差异报告](https://github.com/pengchujin/aerial-tv/issues/121)，它来自 Android 6，不能当作 S50 Air 的验收。普通 alias 的处理继续保留；实际 APK 的 `windowHomeGuard.targets` 才是该包已有能力的证据。

另有 [X50 Air Android 4.3 的社区报告](https://github.com/pengchujin/aerial-tv/issues/1172)指出 `DesktopManagerService.startDockOrHome` 显式启动 `com.stv.launcher/.activity.Launcher`，绕过默认 HOME，停用后没有回退。以及 [S40 Air 精简固件报告](https://github.com/pengchujin/aerial-tv/issues/1118)使用同包名应用承接已缺失的原桌面。它们是不同固件的调查参考，不授予 S50 Air 禁用或同包名替换资格。签名、原件、依赖及恢复仍按上方空壳调查逐项核对。

对方电视不在本机时，可交付独立的 [只读采集脚本](../../scripts/collect_letv_home.py)，只需要 Python 3 和已有 ADB。先列出设备、让用户确认目标，不扫描网络或照搬报告旧地址。当前用户未知时省略 `--user`，不猜0；已有任务且用户已核对时，通过原任务执行：

```sh
python3 agent_session.py run --session "$SESSION_DIR" --tool collect_letv_home -- --seconds 90 --pull-files
```

尚未建立任务、旧固件无法确认当前用户时，独立采集到全新私有目录：

```sh
python3 collect_letv_home.py --adb "$ADB_PATH" --serial "$TV_SERIAL" \
  --record "$NEW_PRIVATE_CASE" --seconds 90 --pull-files
```

脚本先开日志流再做只读快照，看到“已开始采集”才安排用户从一个应用按一次实体 HOME，并记下时间、原页面及返回页面。复现窗口默认90秒、最多180秒，不含前后快照耗时；Ctrl+C停止并保存。没有清日志、PID过滤、按键注入、应用广播、安装、root、权限写入、包停用或重启。查询被拒绝、无当前用户、日志提前结束、截断及省略长行分别保留，退出码0也不表示HOME验收通过。

`--pull-files` 仅保存 `pm path` 实际返回的原包 APK、Quiet TV APK，以及明确的 `/system/framework/framework-letv.jar` 和 `.odex` 候选；失败保持缺失，不尝试提权。前后设备身份未能确认一致时不拉文件。未指定该选项时只保存日志与快照。副本不执行、不修改、不上传；存在文件或字符串不代表已经证明显式路由，更不代表签名可覆盖或恢复可用。

读取 `session.json`、`report.json`、前后快照和日志，将用户观察关联到真实前台／启动组件。框架及原厂APK没有自动脱敏，日志也只尽力处理常见凭据和网络标识；全部资料仅在电脑私下保存。脚本的反馈报告是待人工补全的调查材料，系统默认HOME、窗口接管、同包名替换与实体场景必须分开记录。该源码修复和新采集工具没有因本地准备而自动发布或安装到用户电视。

### API19 本机 ADB 桌面守护

新开发包的 `adb-home-guard-v1` 将电脑脚本的观察循环移到电视端，仅用于 API19 兼容档，默认不启用。通过应用已有的本机 ADB 连接，以当前用户唯一的 `mResumedActivity`、当前焦点窗口和原桌面完整组件判断前台；后台历史包名不触发。每次原桌面前台事件只尝试一次，启动后核对 Quiet TV 前台；屏幕关闭、锁定或屏保时不启动。不禁用原桌面，不改变系统 HOME，不修改 ADB 开关或端口监听状态。

Agent 先通过同次工具包建立／继续任务，读取实际 APK 的能力及原恢复记录，核对本机原桌面完整组件、固件与实际 TCP 端口；不得把示例或其他电视的地址、包名及端口直接套用。旧 APK 缺能力时明确报告需要新包，不能只更新脚本后宣布支持。使用现有 `install` 路线（基础试用已通过）或 `repair --issue home`，通过任务工具执行预览及配置：

```sh
python3 agent_session.py run --session "$SESSION_DIR" --tool device_maintenance -- repair --adb-guard --home "$ORIGINAL_HOME" --port "$LOCAL_ADB_PORT"
python3 agent_session.py run --session "$SESSION_DIR" --tool device_maintenance -- repair --adb-guard --home "$ORIGINAL_HOME" --port "$LOCAL_ADB_PORT" --apply
```

已暂停时仅按用户明确恢复目标追加 `--resume`。配置会请求应用自己的 ADB 授权，若系统实际弹窗则请用户确认；不复制电脑密钥。应用复用进程共享连接，开机及升级后只恢复先前启用的守护，固件变化停止启用。通知可进入状态及暂停入口；“暂停桌面接管”同时停止该守护。此路线的恢复只需暂停，脚本不写回系统 HOME；原桌面可从帮助恢复页打开，实体 HOME 仍须验收。

配置读回只证明选项保存。须关闭电脑守护后分别验证本机 ADB 连通、真实跳转、实体 HOME、重启／冷启动、待机唤醒及视频／HDMI／设置不被打断。若固件重启关闭 ADB 端口，应用无法通过已关闭的通道恢复自身连接，报告受限；不以常驻服务或成功启动一次替代这些验收。此能力与 API21 以上的无障碍守护、ADB 开关恢复是独立路线。

默认安装请求包含 ADB 常开，不需要用户在电视桌面设置开关。独立修复 ADB、同时保留现有桌面路线和暂停状态时：

```sh
python3 configure_home_guard.py --serial "$TV_SERIAL" --user "$TV_USER" --package "$QUIET_PACKAGE" --adb-only --keep-adb
```

预览后在已有授权内用 `--apply --record "$NEW_PRIVATE_RECORD"` 执行。工具先保存原权限、开关和应用选项，核对实际能力，再授予写安全设置权限并持久保存保持选项；读回应用状态及 `adb_enabled=1` 才确认配置步骤。此路径不授予守护所需的无障碍、悬浮窗或使用统计权限，不改变原桌面和暂停状态。

用户明确要求停止保持时，独立命令改用 `--no-keep-adb`，只停止自动恢复，不主动关闭当前连接或删除授权；这与安装入口的同名参数“本次不新增开启”语义不同。默认流程不自动执行此操作。

配置和验收分开：记录固件、当前连接方式、实际端口和 `/proc/sys/kernel/random/boot_id`；用户授权重启测试后，通过原授权连接重新建立 ADB，核对同一设备、变化后的 boot_id、`adb_enabled=1` 和应用内 `adb.selected/ready/settingEnabled`。网络模式还须通过实际网络地址重连，不能用 USB／模拟器串行通道成功代替。冷启动和待机唤醒分别验证。断连后不得盲目重启、反复开关或扫描网络；无法重新连接时通过电视系统授权或已知 USB 恢复路径继续，并报告未通过。

## 原桌面实际页面观察

原桌面恢复目标保持为所选 HOME 入口。运行时同时识别有效的入口及 Activity alias 目标；其他跳转页面仅通过本机精确适配规则加入，不把同包所有页面或所有 HOME 候选当作桌面。输入播放器、儿童应用和已知工厂测试入口不作为观察目标。

现有 `home` 规则可附加 `observation`：必须限定品牌、型号、完整固件、原桌面版本及用户，`preserveOriginal=true`；观察对象需 `verified=true`、HTTPS 证据来源，以及 `targets` 数组，每项为实际 `component` 和 `versionCode`。规则由现有适配入口保存，执行前仍检查组件及系统包可用性和版本。包更新、禁用、卸载或规则变化会重新计算目标，使对应旧场景证据失效；扩展观察依赖的包受保护。主动打开原桌面时，允许的原桌面包均暂时放行。

[Aerial 固定源码中的跳转页面参考](https://github.com/pengchujin/aerial-tv/blob/587a2849c58b27dc5854a18eab3b458e1d072b34/app/src/main/java/app/orchard/tv/guard/HomeGuardService.kt)包括乐视 `com.stv.deskplatform.ui.activity.Launcher`、腾讯极光 `com.ktcp.launcher.activity.LauncherHomeSingleTaskActivity`。这里只记录候选来源，没有加入 QuietTV 已验收执行规则；本机页面用途、固件、组件版本和实际行为须分别核对。

## HOME 后窗口事件失效

收到系统 `homekey` 广播且已配置的 HOME 路线可用时，延迟 250 毫秒显式返回 Quiet TV，不再等待新的窗口或用量统计事件。期间到达的其他窗口不取消这次明确的 HOME 动作；暂停、息屏、切源、主动打开原桌面或首页已显示仍会取消。已在首页或已有启动请求时由统一入口去重。该广播不能单独证明实体按键已验收；遥控器短按、长按、连按和外设过滤仍沿用原分流。

保留原桌面或代理拥有系统 HOME 时，以普通 Activity 身份打开 Quiet TV；系统 HOME 属于 Quiet TV 时保持原生 HOME 启动方式。被动窗口、用量统计和开机／唤醒检查仍要求新鲜、精确的原桌面前台证据；退出前台、其他应用及未知前台不触发接管。

启动异常或等待首页回调 5 秒超时后，500 毫秒后最多补偿一次。补偿重新核对路线、暂停、屏幕和前台；被动接管要求仍有新鲜的精确原桌面证据，明确 HOME 动作则在没有后续用户导航或更新的其他前台证据时保留。暂停、切源、导航、服务断开或首页已显示取消补偿。唤醒检查遇到已有启动请求时仍沿用该请求的超时处理，不增加并行请求，不因窗口事件已消费而永远失去补偿机会。

精确适配规则的 `observation.silentUsage=true` 可启用已有每秒观察路径，息屏停止；没有本机证据不对新品牌启用持续观察。运行中恢复仅移除并重新加入自身无障碍登记，每个开机身份至多一次，并与已有恢复请求互斥；旧小米全局切换专项没有扩大范围。

自身服务的延迟移除／重新登记会比较本次写入后的服务列表、总开关及恢复请求身份。期间设置变化时停止自动续办，保留 AUTO／OFF，维护快照以 `recoverySettingsChanged` 标记，明确重新配置或恢复接管后才解除。旧小米 API21–23 总开关刷新仅在没有其他已登记服务时使用，否则退回自身服务恢复；延迟恢复前再次核对列表和总开关，不覆盖更新后的选择。

## 开机页面晚覆盖与初始化等待

`home.observation.bootTargets` 使用与 `targets` 相同的组件／版本格式，仅在真实开机后的 180 秒窗口内识别；PatchWall `com.mitv.tvhome.BootActivity` 等上游页面只是候选，未取得本机证据时不加入执行规则。保留开机后 30／45 秒检查，时间按本次开机计算，不因服务重建重新开始。`bootStockMs` 默认为 0；本机验证确实需要原桌面初始化时可设置 0–60000 毫秒，从第一次实际观察到原桌面开始等待。等待跨进程保留，用户导航、切源、暂停或前台变化会取消相应检查。

服务在 45 秒之后、180 秒以内才绑定时，补一次当前前台检查。实际观察到息屏再亮屏后，清除息屏前的窗口证据，并在 5 秒后有限复查一次；仅接受本次唤醒之后的新鲜原桌面证据，不把 HDMI、播放器或未知画面当作原桌面。升级中未完成的既有代理握手可在解锁或亮屏后再次核对，仍受原路线、身份与 AUTO／OFF 状态约束，不改变暂停选择。

守护另在设备保护存储保存观察到的息屏及本次开机身份。待机中服务或进程退出后，重新绑定可续办这次唤醒检查；若没有收到亮屏广播，以已记录的息屏时间排除旧证据，仅检查最近的明确原桌面前台。绑定本身不产生唤醒，重启前记录不沿用；续办窗口最长 15 秒，重建不延长，检查完成或用户导航、暂停后清除。无法核对开机身份时不猜测。

启动应用或已测试的标准 HDMI 发出启动请求后，还必须观察到对应目标前台，再观察到明确的原桌面／开机页面覆盖，才会在启动后 60 秒内补偿一次。次数、目标及开机身份持久保存；用户 HOME、导航、切源、其他应用、暂停或配置变化会停止补偿，进程重建和待机唤醒不当作新的开机。再次进入 QuietTV 后沿用原自启入口及儿童模式检查；目标不可用时保持桌面，不循环启动。

标准 HDMI 需要核对当前信号源身份和实际播放器组件。私有厂商信号源没有可核对的前台组件时不启用此补偿；不会因最后一个应用退出或出现未知黑屏就推断应重新打开信号源。能力查询通过 `home-observation-v1` 区分支持本批观察规则的 APK；旧包拒绝写入新规则，避免工具成功但运行时忽略字段。


## HOME 按键过滤与外设

`home.observation.filterHome=true` 可在 API21–30 且服务具备过滤能力时扩大 HOME 过滤，沿用精确固件、原桌面版本、用户和验证来源约束；未匹配规则时保留既有机型策略。需要先取得本机 HOME 延迟或露出原桌面的证据，不按 TCL 品牌批量启用。删除此字段或设为 false 即退回原策略。工具仅向声明 `home-key-filter-v1` 的 APK 写入此字段。

服务监听输入设备增加、移除和变化。手柄以真实 GAMEPAD 来源识别，不把只有 JOYSTICK 标记的红外遥控器或虚拟语音设备算作手柄；手柄连接且前台不是桌面时停止过滤。小米输入栈连接鼠标时停止过滤，API29 以下无法确认外接属性时对物理鼠标保守放行。外设移除后重新核对当前路线、前台和权限再恢复。正常系统默认 HOME 且没有专项按键补偿时不请求普通 HOME 过滤。

诊断中的 `keyFilterReason` 区分输入拓扑未知、小米鼠标保护、手柄不在桌面、系统原生 HOME、能力缺失及屏幕不可用；只记录原因变化，不记录连续输入流。尚无可靠输入来源及机型证据时保留这些保护，不直接改为全局拦截遥控器、鼠标和手柄的 HOME。

其他按键继续透传；已接收的 HOME 按下／抬起保持配对，期间暂停或条件失效则不触发动作。短按、长按和双击沿用现有语义；不会修改其他无障碍服务登记。依据 [Android 输入设备接口](https://developer.android.com/reference/android/view/InputDevice) 和 [输入设备监听接口](https://developer.android.com/reference/android/hardware/input/InputManager)；软件用例不能代替厂商鼠标／手柄插拔与输入栈稳定性验收。


## 设为桌面与状态入口

桌面设置中的“设为桌面”和“帮助与恢复”打开同一页。页面只读取现有路线、系统 HOME 和当前配置的场景确认记录，不授予权限、不恢复暂停状态、不重新配置守护。系统默认桌面选择入口可用时直接打开；其余配置沿用公开安装页二维码和电脑 AI 流程。仅选择 Quiet TV 或收到首页回调时保持待验证；HOME、重启、断电开机、唤醒四项当前记录均通过，包含确认时间和证据编号且配置有效，才显示“已验证可用”。

`DEVICE_MAINTENANCE` 的 `home-status-v1` 能力和 `desktopStatus` 返回同一状态。旧 APK 没有该能力时电脑端显示未提供状态，保留旧维护路径，不从 `guardConfigured` 推断成功。配置未完成、已暂停、已失效及能力受限分别提示下一步；进入状态页不会自动修复。

“导出诊断”沿用现有局域网下载及脱敏日志，不自动上传。观察事件仅在已匹配的原桌面／开机页面上记录目标组件，关联既有 observation 和 attempt；导出补充权限缺项、恢复检查次数与停止原因。`requestToCallbackMs` 表示启动请求到首页软件回调的耗时，`screenVerified=false`，不能替代实体 HOME 或用户可见画面验收。不记录完整前台应用流或通知内容。
